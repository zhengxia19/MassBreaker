# 工程规范、依赖与变更控制

**编号** MB-ENG-001

## 1. 工程实施规则

- 首选简单、可读、可维护的 C++20；避免提前抽象、框架堆叠和重复的防御逻辑。
- 稳态物理、帧收集及 CPU 实例构建不进行堆分配/释放；缓冲容量在加载阶段按上界确定并复用，记录总内存。物理热路径不做文件 I/O、日志格式化/打印、音频解码/播放或 OpenGL 调用。
- 不为每个 tick 创建定时器；FrameScheduler 统一阻塞等待和呈现节奏。静态页面和后台无周期游戏工作；性能优化直接按设计实施。
- 先采用有序紧凑数组、增量维护及正确性等价快速路径；每项优化保留回归依据，不以丢弃权威事件或改变时间步长节能。
- 物理核心独立于 SDL3，便于桌面单测；禁止把游戏逻辑写入 Android Activity。
- 渲染只读状态；所有砖块扣血和道具事件通过 `Simulation` 入口发生。
- 依赖库必须固定版本，升级单独提交并记录影响。
- V1 不主动引入 ECS、Box2D、并发任务框架、全局服务定位器和通用插件机制。

## 2. C++ 代码规范

- 类/结构体用 `PascalCase`；方法和变量用 `camelCase`；文件名 `snake_case`；常量采用 `kName` 形式。
- 优先 RAII 与 `std::vector`/`std::array`/`std::unique_ptr`，避免裸拥有指针。
- 每个模块有明确所有权：例如 `BrickField` 独占砖块状态，`BallPool` 独占球数据，Renderer 独占 GL 资源。
- 错误处理：加载/初始化阶段清晰返回错误，热路径只做必要边界保护；不在每一层重复记录相同错误。
- 使用 `clang-format` 固定仓库配置，编译开启合理告警；Debug 启用断言与可用的检测工具。
- 坚持确定的球遍历顺序，随机效果采用保存的种子，不把 `std::unordered_map` 的非固定遍历顺序用于规则判定。
- 使用浮点数进行运动计算，接触容差与最小速度阈值集中配置，不能散落硬编码。

## 3. 代码组织与提交

- 主分支为 `master`；T01 建立可编译基线后保持其构建通过。开发使用短分支 `codex/Txx-topic`，通过审查后合并。
- 每个任务只交付与其范围有关的代码/资源/文档及验证；文档和资源任务不强制附加源码变更或单测。不同要求可以引用同一有效证据，不为凑任务产物重复工作。
- 提交消息建议 `feat(physics): ...`、`fix(level): ...`、`docs: ...` 等，关联任务编号。
- 大文件资产（视频参考文件、原始素材）不直接混入游戏包；正式资源保持可重建、可追溯。
- 机密签名文件、keystore、配置密钥、临时构建产物均在 `.gitignore` 排除。

## 4. 内容与资源管理

- 每关保留 Tiled 源、运行时 JSON、对应简短设计说明；导出资源可用工具重建。
- 不从 X 视频直接提取受限制的图案、美术或声音作为游戏发布素材；仅借鉴公开可见的通道和砖阵设计思路，自制图形与音效。
- 字体、音效、图片的版权及许可证须记录供应商/来源、类型、范围；当前项目不包含任何字体二进制文件。
- 关卡变更需要同步检查目标砖计数、道具位置和通关可玩性。

## 5. 变更控制

以下改变需要修改 PRD、架构及任务计划，而非在功能分支中悄悄增加：新增第二种主要玩法、球球碰撞、移动墙、多平台在线账号、广告内购、观看加速、改变星级规则、修改运行时关卡 schema、改变弹球硬上限。

调整颜色、单关布局、音量、UI 文案等局部内容，不需要完整 ADR；只更新相关资源或关卡说明即可。

## 6. 完成定义

“完成”必须意味着：需求得到满足、相关编译或资源/文档校验通过、受影响关键行为已检查、必需资源与文档齐全，且没有引入当前项目范围外的复杂结构。不要把“代码合并”本身当作交付完成。


## 7. 文档维护

- 文档只描述当前有效需求、接口、任务与验收状态；直接修订所属正文，不追加按版本排列的补丁章节。
- 同一规则只在所属规范中定义，其他文档引用它；参数以配置文件为准，公共类型以算法文档为准。
- 更新实现状态时记录实际命令、工作区、日期和证据边界；待实现用例不得写成已通过。
- 关卡调整同步源图、JSON、manifest、预览及相关规格；实现行为改变同步对应测试和验收要求。
