# 功能测试、关卡验收及发布质量门槛

**编号：** MB-QA-007｜**性质：** 与开发任务绑定的常规质量保障，不单设大型技术研究。

## 1. 分层验收范围

| 层次 | 已交付证据 | 开发期间还需交付 |
|---|---|---|
| 文档与资源静态 | 30 Tiled/JSON 对照、schema、marker、固定墙可达性基本检查 | 代表性地图的 Tiled 打开/编辑/保存/导出冒烟检查；无需逐图重复 GUI 操作，数据改动运行工具校验 |

## 2. 核心算法验收

单测优先覆盖 [`12_CORE_ALGORITHMS.md §11`](12_CORE_ALGORITHMS.md) 的 **ALG-01 至 ALG-14**，以及 §12–§16 的 **CTRL-01..05 / FRAME-01..06 / LOOP-01..09 / API-02 / BONUS-01..02 / STAT-01..05 / PERF-01..10**。特别是：高速穿过细砖、擦过圆角但未碰撞、双砖同时间接触、两球同一物理步毁同一块砖、B 拾取时最后球掉出、最后目标与最后球同 tick 消失、1024 上限的积分补偿。

碰撞与奖励用例需给定相关起点、速度、球 ID、砖格及预期 HP、积分、球数；其他用例只给其行为所需输入，不使用难以复现的视觉观察代替测试。需要时引入一个固定 seed，记录 `tick/id/position/HP/score` 最小事件日志。

## 3. UI 与交互验收

八种页面与状态按 [`10_UI_UX_DESIGN.md`](10_UI_UX_DESIGN.md) 及 [`14_VISUAL_DESIGN_AND_FEEDBACK.md`](14_VISUAL_DESIGN_AND_FEEDBACK.md) **按能力验收**：T10 页面/交互、T11 真实存档、T12 正式资源与产品集成。T11 在 T03 后可与 T10 并行；真实资源/保存接口就绪时直接接入，不强制先做占位实现。同一有效证据复用，T12 补集成路径及受影响检查。**不得在 T10 时提前声称完整 UI 产品验收通过。**需检查 360×640、360×800 和至少一台实际 Android 高 DPI 屏幕。主要检查安全区、挡板移动时指针捕获、轻点才发球、多指不劫持、系统返回打开暂停、后台恢复无跳帧。

保存失败必须明确提示；重启后已解锁与最佳成绩持久化。L030 成功页不显示无效的“下一关”。失败页使用核心权威 `initialTargets/destroyedTargets` 及 V1 生命耗尽文案，按 `STAT-01..05` 验证；UI 不自行累计击毁事件。

## 4. 关卡验收（正常内容制作流程）

- 30 关均从真实资源 JSON 加载，实际画面与渲染预览的砖块/墙位置一致。
- 所有关卡**至少人工通关一次**；多入口、疑似卡球或路线失衡的关卡补充另一策略试玩，不按固定名单重复。通过记录可在任务间复用；影响可玩性的改动须重测对应关卡。
- L001–L004 验证单球可击中主要砖阵，无长时间无法触及的目标；L005 能实际击破 B 并接到 +3；后续关卡存在可获得的多球过程。
- 关卡修改后更新受影响的导出与预览，执行全量轻量数据校验；人工试玩只重测受影响关卡。导出器、全局玩法或碰撞改变时再扩大回归范围。
- 记录关卡/资源标识、机型、完成结果、耗时与关键问题；首次 B 接取时间、拾取数和峰值球数由调试计数自动采集或在平衡诊断时补充。静态数量引用 manifest，不人工抄录。

**结构检查与可玩性严格区分：** `geometry.py` 假设目标砖最终可移除，只证明没有明显的固定墙封闭，不能证明特定入射角、过关时长或球永不被困。

## 5. 性能与设备检查

**PLAYING 目标为 60 FPS，物理固定 120 Hz；静态 READY/菜单/暂停/终态按需更新，后台停止游戏 tick 与呈现。FPS、tick 和线程唤醒次数分别测量。**以下阈值是项目发布前的**验收要求**，不是已有真机跑分；实测未知。

### 5.1 基准设备与测试范围

- **重点设备 A**：参考 Snapdragon 855 / 6 GB RAM 档位，使用实际可取得且代表支持下限的设备，记录型号、SoC、内存、Android/build、分辨率与实际刷新率。替代设备的能力差异须说明；更强设备通过不证明较弱档位通过，不把参考机型采购设为开发前置条件。
- **辅助设备 B**：另一 SoC/系统版本的 Android arm64 真机，检查安装、显示、触控、生命周期与代表性高负载。出现帧节奏、发热或驱动异常时扩展为完整性能测试；不机械复制 A 的全部长测。
- 使用 Release 或同等优化构建，固定并记录配置、亮度、音量、供电与显示模式。采样排除首次资源加载及菜单时间，保留实际掉帧与困难阶段。
- 从真实 L016/L028/L030 检查密集砖阵和多球负载，以实测选择代表性高负载作持续测试；不能仅凭关卡编号认定最坏负载。记录实际球数、目标数、拾取数及操作步骤；已有输入回放可复用，不为此另开发完整录制回放系统。

### 5.2 采样与通过阈值

日常修改只执行受影响的自动测试、构建和必要真机检查。T08/T09/T12 保留轻量帧时间、分配与唤醒记录，发现异常即分析。T16 发布候选执行完整验收；物理、渲染、调度或资源负载重大变化时提前执行相关完整测试。

正式测试前登记预热方式、采样时长、有效 PLAYING 区间、负载覆盖及停止条件。时长应覆盖代表性多球与连续运行状态；短功能冒烟不能作为持续性能证据。若关卡提前结束，记录重开间隔并合并有效区间；不将暂停/菜单计入平均 FPS。

按单调时钟记录实际展示帧间隔，保留原始样本、平均 FPS、P50/P95/P99、最慢帧与 SimulationOverload 时间点；CPU draw 耗时不能冒充展示帧间隔。系统展示时间不可获取时说明数据来源与限制，不标为已验证展示节奏。

| 指标 | 重点设备 A 的正式通过阈值 | 判定说明 |
|---|---|---|
| 平均 FPS | ≥ 58 | 目标 60 FPS，统计有效 PLAYING 区间 |
| 帧间隔 P95 | ≤ 20.0 ms | 覆盖真实多球阶段 |
| 帧间隔 P99 | ≤ 33.4 ms | 同时查看卡顿分布，不用平均数掩盖问题 |
| 非预期 SimulationOverload | 0 次 | 正常关卡触发即失败，不靠安全暂停满足帧率 |

P50、最慢帧和过载发生分布用于诊断，不另设 P50 或滚动过载次数门槛。B 的代表性负载若不能达到上述指标，也须定位并处理；不得只引用 A 的合格数据。

1024 球容量及缓冲边界必须做短时正确性/分配检查，不要求该合成极限负载单独做长时间功耗测试。`10,000 格 + 300 球` 仅在诊断需要时使用。不得删除有效球、跳过 CCD 或增大物理 dt 来通过验收。

### 5.3 共用验收记录

同一次运行可同时提供功能、帧时间、分配、热状态和可用功耗证据；多个任务引用同一记录，不分别抄写报告。

| 字段 | 内容 |
|---|---|
| 运行标识 | 构建/工作区标识、配置和关卡标识、日期、设备/OS、操作步骤或既有回放 |
| 条件与范围 | 显示模式、亮度/音量/供电、预热及有效区间、负载覆盖、停止条件 |
| 结果 | 平均 FPS、P50/P95/P99、最慢帧、过载/异常；按改动范围附分配与唤醒结果 |
| 持续与功耗 | 持续测试的温度来源/趋势、末段帧时间；可测时记录功率/能量、测量边界、误差与重复样本 |
| 判定 | 各必要项结果、问题与复测、缺失设备能力或未验证范围 |

缺少有效负载或未满足预先登记的停止条件时，持续测试标记未完成。未测得功率不妨碍记录其他检查通过，但不得声称已验证能耗或省电比例。

### 5.4 功耗、空闲行为与持续运行

| 项目 | 方法与通过条件 |
|---|---|
| 静态与后台 | READY 无输入、菜单/暂停/结算动画结束后，真机观察是否存在周期游戏工作；60 秒可作为冒烟观察窗口，自动单测用可控时钟。隔离系统暴露事件后游戏自建周期 tick/呈现为 0；后台游戏 tick/GL 提交为 0，恢复正常。音频设备回调和系统线程单列。 |
| 稳态分配 | 核心模拟、收集器、CPU 实例构建在单球、代表性多球及 1024 球短时压力下无堆分配/释放；记录容量推导和峰值。加载、SDL/驱动开销单列；仅缓冲、实体或相关热路径改变时重测。 |
| 开发阶段测量 | T08/T09 首次可玩时记录帧时间、分配、唤醒及设备可提供的功耗数据；T12 增加正式效果后查异常。不要求每阶段重复正式功耗对比，功能不同的构建不能直接归因节能收益。 |
| 正式功耗对比 | 用于验证优化收益或排查能耗回归时，固定设备、OS、亮度、实际刷新率、音量、网络、关卡、输入、配置和初始热状态；候选/参考交替采样。各 3 次可作为初始样本，按重复波动判断是否足够；不确定则增加样本或标记结论不足。记录功率 W、能量 J、有效时长及测量边界，不混比整机与电源轨。 |
| 测量能力 | 支持时使用设备电源轨或校准外部设备；缺少能力时精确功耗标记未验证，不阻断其他开发任务或单独阻断发布。CPU/温度仅作代理，电量百分比不单独证明节能幅度；如交付宣称具体省电收益，须先补齐相应证据。 |
| 回归处理 | 同功能同条件比较，超出预先登记测量误差的能耗上升须复测定位；确认由本次改动造成的回归须修复或在记录中说明必要成本与对应验收结论。初次测量不自动成为所有后续功能不可突破的永久能耗上限。 |
| 持续运行 | A 对代表性高负载持续运行；测试前登记观察窗口和温度/帧时间稳定判据，至少连续两个观察窗口无持续恶化，再核对末段满足 §5.2。温度或帧时间仍在恶化就延长；无法证明趋稳时如实标记范围不足。无温度读数时保留持续帧时间和系统可用热状态，不能声称温度已稳定。B 按异常与硬件差异扩展持续测试。 |
| 视觉降载 | 热状态适配用可注入状态检查降载逻辑和 API 不可用回退；真机验证可用接口，无需只为 API 两分支另备专用机。降载不改变物理 dt/球数，不降低核心可辨识性；配置与触发时间单列，不能混入固定画质功耗比较。 |

静态停工、帧节奏、内存稳定与持续运行是必验项；精确能耗按实际测量能力给出独立结论。60 FPS 通过不等于功耗通过。

官方方法参考：[Android 功耗优化](https://developer.android.com/games/optimize/power)、[帧节奏](https://developer.android.com/games/sdk/frame-pacing)、[Power Profiler 测量边界](https://developer.android.com/studio/profile/power-profiler)。

## 6. 发布质量门槛

| 级别 | 典型问题 | 允许发布？ |
|---|---|---|
| Blocker | 无法打开/关卡不可完成/数据损坏/系统性穿砖 | 否 |
| High | 道具不触发、错误扣命、严重持续掉帧、暂停失效 | 否 |
| Medium | 少量动效错位、偶发非阻塞音效错误 | 修复或明确记录后评估 |
| Low | 非必要装饰瑕疵 | 允许登记后改进 |

最终产物：Windows 构建记录、Android debug APK 与 release APK/AAB、30 关人工试玩记录、关键单测结果、资源授权清单、真实机型/帧时间记录、Git commit/签名与版本记录。设计文档和地图通过静态测试，**不等于已经完成这些发布条件**。
